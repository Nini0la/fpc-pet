# Architecture

## Milestone 3 boundary

One FastAPI service and one Next.js app use PostgreSQL as production authority. SQLite remains limited to isolated API/unit tests. There is no broker, vector database, graph orchestration engine, or private FPC machinery. Conversation segmentation is internal; chat, morning briefings, and evening check-ins share one continuing relationship.

`AgentRuntime.handle(RuntimeEvent)` is the only event entry point for user and scheduled events. `MorningBriefingSkill`, `EveningReflectionSkill`, and `ProspectiveReminderSkill` are thin deterministic skills called by that runtime. A transaction records the `AgentEvent`, `SkillRun`, proactive/user messages, journal/state mutations, Episodes, and provenance together. Versioned `v2:` request fingerprints bind the user, event kind/payload/date, and normalized conversation target for user messages: the same idempotency key replays only for the same target and conflicts if retargeted. A pre-`0003` unversioned fingerprint is accepted only when the exact legacy canonical request matches; user-message replay additionally requires the target conversation to belong to that user. A successful legacy replay upgrades the stored fingerprint to v2, so later comparisons never use the weaker form. Model proposals never receive an ORM session. `ModelRouter` remains the future live-provider boundary; deterministic replies are explicitly development/test-only.

### Daily loop

`User.timezone` plus an injected timezone-aware clock and `zoneinfo` determine local dates, including DST transitions. `DailyBriefing` persists the rendered briefing, named non-empty sections, structured Power List, source event, policy version, and chat message. A unique `(user_id, local_date, policy_version)` constraint is the logical morning idempotency authority. `ReflectionPrompt` applies the same pattern to evening check-ins and tracks `awaiting`/`completed` state. The authenticated scheduled-event boundary accepts `intended_local_date` only for morning/evening events and only for the current or immediately previous user-local day; this supports a missed-trigger catch-up without reassigning the record to execution day. Repeated catch-up triggers for that intended day do not duplicate proactive messages.

The M2 `m2-v1` Power List remains bounded and stable. M3 adds a separate `m3-v1` urgency calculation with exact reason factors: deadline hours, estimated effort, schedule slack, importance, inactivity, blocked-dependency count, and stored availability only when present. Inactivity is measured from `Commitment.last_touched_at`, which is refreshed by meaningful user/runtime/API mutations but not by read-only listing or reminder scans; legacy rows backfill it deterministically from `created_at` because the M2 commitment schema had no `updated_at`. Scores map deterministically to low/medium/high. Date-only deadlines use 23:59:59 in the user's local timezone while retaining explicit date granularity and source phrase. Recognized but invalid ISO dates or clocks retain that source phrase, store no `due_at`, and produce a bounded clarification instead of an exception or guessed deadline.

### Prospective memory

`commitment_check` accepts an optional timezone-aware intended instant and bounded catch-up window, then executes through the same runtime transaction. The reminder skill scans at most 100 tenant-owned, non-deleted, non-terminal, unambiguous commitments under row locks. Immediately before surfacing it refreshes and re-checks authoritative state. A unique `(user_id, commitment_id, relevance_window, policy_version)` key provides durable at-least-once idempotency. A surfaced bundle contains one same-chat assistant Message, Reminder, Episode, SkillRun, AgentEvent, and metadata-only provenance; reason metadata contains numeric factors rather than copied raw chat. Retry state is bounded to three attempts. The demonstrative completion “Actually, I finished that already” mutates only a uniquely most-recently surfaced active commitment; no surfaced candidate or a tie produces clarification and no mutation.

An evening answer is stored unchanged in `JournalEntry.original_content`, with optional summary and structured supported changes, source message/event, UTC timestamps, and the matched prompt's local date. The answer binds to the user's most recent awaiting prompt created within the preceding 12 hours, so midnight and DST crossings preserve the prompted day. Extraction is clause-aware but narrow: exact normalized subjects, explicit contrast/negation, safe action/article normalization, and `it` only when one supported subject appeared in the immediately preceding clause. Ambiguous references cause no mutation. Structured updates and sourced Episodes occur in the same transaction. The following morning excludes completed commitments and boosts still-open items explicitly marked unfinished.

### Persistence and APIs

All durable records are UUID-owned by a user and tenant filters are mandatory. The current product model has exactly one persistent `ConversationSession` per user, enforced by a unique `user_id`. Creation is conflict-safe, and every message append locks that tenant-scoped conversation row before allocating the next ordinal. A unique `(conversation_id, ordinal)` constraint is the final ordering authority, so concurrent proactive and user-message transactions remain in one chat with distinct, strictly increasing, transaction-contiguous ordinals. Mutable threads, commitments, and episodes retain versioned correction/deletion behavior. Derived state has confidence, derivation, and `ProvenanceLink`; audit rows store observable action/reason metadata, not hidden chain-of-thought or prompts.

`GET /api/today` returns only the authenticated user's local-day briefing, Power List, resurfaced items, reflection state, live commitment urgency, and stable oldest-first slices of open commitments and active threads. Each state slice is capped at 50; `collection_meta` supplies `limit`, `returned_count`, `total_count`, and `has_more`. Persisted briefing collection sections are also capped at 50 and include equivalent metadata for commitments and threads. `GET /api/history/journals` and `GET /api/reminders` are tenant-scoped with bounded query/pagination. The Next.js page renders a minimal Today surface alongside chat; full navigation/polish remains M5.

PostgreSQL is migrated with explicit Alembic revisions. `0001` is the M1 foundation; `0002` adds the daily loop; reversible `0003` establishes conversation concurrency invariants; reversible `0004` adds normalized commitment timing/effort/urgency fields and Reminder persistence. Before restoring the M2 state constraint, `0004` downgrade applies the documented loss-aware mapping `in_progress|waiting → open`, `completed → complete`, and `cancelled → abandoned`; already-M2-valid states are unchanged. Re-upgrade preserves those mapped valid states.
