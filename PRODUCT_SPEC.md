# Personal AI Product Specification

You are building a small but coherent personal AI product for a hackathon.

The product should NOT attempt to implement a full general-purpose personal operating system or reproduce any proprietary FPC architecture.

Instead, it should demonstrate one narrow idea extremely well:

**A personal AI should carry important things forward through time.**

It should remember selectively, track unfinished threads and commitments, notice when time changes their urgency, help orient the user in the morning, integrate what happened in the evening, actively help the user learn over time, and accurately recall what the user and assistant have done together.

The product should feel like a long-lived personal AI relationship, not a chatbot with a vector database.

## 1. PRODUCT THESIS

The core experience is:

```text
live
→ say things naturally
→ some things become meaningful persistent state
→ time passes
→ the AI notices when something becomes relevant
→ it resurfaces, asks, reminds, searches, or acts
→ the user responds
→ the AI updates its understanding
→ repeat
```

The product should demonstrate continuity across days.

The most important behaviors are:

1. selective persistent memory
2. unresolved-thread tracking
3. prospective memory / timely reminders
4. morning orientation
5. evening reflection
6. accurate shared-history recall
7. longitudinal vocabulary learning
8. proactive behavior based on time and changing context

The governing product principle is:

> “The AI carries important things through time with the user.”

Whenever choosing between adding more features and improving continuity over time, improve continuity.

## 2. CHAT EXPERIENCE

The product has one primary, persistent conversational relationship between the user and their personal AI.

Do NOT make “new chat” the fundamental interaction model.

The user should be able to return tomorrow, next week, or next month and continue talking naturally without needing to locate the previous conversation containing the relevant context.

Internally, messages may be segmented into sessions for storage, context-window management, summarization, or retrieval, but this segmentation should normally be invisible to the user.

The CHAT view should resemble a simple modern messaging interface:

- chronological messages
- text input
- streaming assistant responses
- timestamps where useful
- optional lightweight cards for commitments, reminders, actions, words, etc.
- mobile-first layout
- ability to reference memories, threads, commitments, and prior episodes

Threads are NOT chat channels.

A Thread represents an ongoing subject, problem, idea, goal, curiosity, or concern in the user’s life. A Thread may be discussed across many conversations and many dates.

TODAY, THREADS, HISTORY, and CHAT are different views over the same underlying personal state.

Proactive messages generated by the system should appear as messages from the same personal AI.

For example:

> “You said the portfolio needs about four hours of work and the deadline is Friday. You now have much less slack than you did two days ago. I think it needs attention today.”

That should feel like the same entity the user spoke to that morning, not a separate reminder service.

## 3. PRIMARY USER EXPERIENCE

The daily rhythm of the product is:

MORNING:
“What matters today?”

DAYTIME:
Conversation, actions, reminders, resurfacing, searches, learning, updates.

EVENING:
“What happened today, what changed, and what should we carry forward?”

The morning and evening experiences should act as bookends around continuity.

## 4. MORNING BRIEFING

Every morning, generate a concise personal briefing based on:

- active goals
- commitments
- deadlines
- upcoming calendar items if integrated
- unfinished work
- threads that have become relevant
- remaining time before deadlines
- recent activity
- yesterday’s unfinished items
- watched threads with noteworthy external discoveries
- vocabulary due for review

The briefing should include a small “Power List”.

The Power List should generally contain approximately 3 meaningful items, not a giant todo list.

The system should briefly explain why each item deserves attention today.

Example:

```text
Morning.

Your Nebius submission closes Friday.
The demo is working, but the evaluation flow is still incomplete.

Power List:
1. Finish evaluation flow
2. Record demo walkthrough
3. Send Patrick the planning document

One thing to watch:
The portfolio task has gone untouched for four days and has less schedule slack than before.

Worth seeing:
A new repository appeared yesterday related to long-lived agent memory evaluation, which seems directly relevant to one of your active threads.

Word of the day:
inchoate — not fully formed or developed.
```

The Power List should be GENERATED FROM STATE.

It should not simply display manually entered tasks.

Potential factors include:

- importance
- deadline proximity
- estimated work remaining
- inactivity
- dependencies
- recent promises
- yesterday’s outcomes
- user priorities
- available time

## 5. EVENING REFLECTION

At the end of the day, initiate an informal conversational check-in.

It should NOT feel like completing a productivity form.

Start naturally, for example:

> “How did things go today?”

The user should be able to answer freely.

Example:

> “Profiling took forever. I finished it but didn’t touch the portfolio. Had lunch with James though and we ended up talking about an interesting idea around local inference.”

From the conversation, update relevant state such as:

- completed items
- unfinished items
- new commitments
- changed priorities
- newly discovered threads
- abandoned or dormant threads
- important events
- useful observations
- outcomes
- blockers

Store the original evening reflection as a journal entry.

Do not reduce the journal only to structured fields.

The user should later be able to browse and search past reflections.

The evening reflection should also include relevant learning loops.

For example:

> “Do you remember what inchoate means?”

> “Did you manage to use it today?”

> “Make me a sentence using it.”

The evening interaction closes the loop opened by the morning briefing.

## 6. THREADS

The system should maintain “Threads”.

A Thread represents something occupying part of the user’s mental space.

A Thread is NOT necessarily a task.

Examples:

- “Should I use Jev for bounded decisions?”
- “Nebius hackathon submission”
- “Maybe learn boxing properly”
- “Long-lived agent memory architectures”
- “Article idea about local AI”
- “Possible UK founder visa route”

Some Threads are highly organized.

Some are vague.

Some have deadlines.

Some have no actions at all.

Some disappear.

Some become relevant again months later.

Do not force every Thread into a productivity ontology.

A Thread should support:

- id
- user_id
- title
- description
- state
- importance
- created_at
- last_touched_at
- optional deadline
- optional next_action
- optional related entities
- optional parent/related threads
- notes/history
- optional watch flag

Suggested states:

- active
- exploring
- waiting
- dormant
- abandoned
- completed

The user should be able to say:

> “Hang onto this idea.”

and have the system create or update a Thread.

The user should also be able to say:

> “I’m not really interested in that anymore.”

and have the system mark the Thread dormant or abandoned rather than simply deleting historical evidence that it existed.

## 7. COMMITMENTS / PROSPECTIVE MEMORY

Maintain Commitments separately from general Threads.

A Commitment represents something the user intends, needs, promised, or expects to do.

Example:

> “Send Sarah the document before Friday.”

Suggested fields:

- id
- user_id
- description
- created_at
- due_at if known
- estimated_effort if known
- importance
- status
- source reference
- next_relevant_moment
- last_surfaced_at
- related_thread_id
- confidence
- ambiguity
- dependencies
- completion timestamp

Suggested statuses:

- open
- in_progress
- waiting
- completed
- cancelled

The system should reason about TIME.

Do not merely trigger reminders at manually fixed timestamps.

It should support prospective memory:

remembering that something needs to happen later and resurfacing it when appropriate.

The system should be able to notice decreasing schedule slack.

Example:

```text
Task:
Finish presentation.

Deadline:
Friday.

Estimated remaining work:
4 hours.

If it is Monday:
low urgency.

If it is Thursday and still unfinished:
high urgency.
```

Implement an initial simple urgency model using factors such as:

- deadline proximity
- unfinished estimated work
- importance
- inactivity
- dependencies
- known availability if available

The exact mathematical model can initially be simple and interpretable.

The system should surface commitments when they become meaningfully relevant.

The user should be able to understand why something was resurfaced.

Example:

> “I’m bringing this up because you said it needs about three hours, the deadline is tomorrow evening, and it hasn’t moved since Monday.”

## 8. EPISODIC / SHARED HISTORY

The assistant must accurately remember what the user and assistant have DONE TOGETHER.

This is more important than trivial preference recall.

The assistant should answer questions such as:

> “What did we decide about the Nebius project?”

> “What have you helped me with this week?”

> “When did we start talking about Jev?”

> “What did we conclude about the IP issue?”

> “What did you already tell me about this?”

> “What have we tried?”

Do NOT rely only on generic vector similarity.

Maintain explicit Episodes or Events.

Each Episode should support:

- id
- user_id
- timestamp / time range
- short summary
- participants
- related threads
- important decisions
- actions taken
- outcomes
- unresolved items
- source references

The assistant should distinguish:

- things the USER did
- things the ASSISTANT did
- things they did TOGETHER
- things merely discussed but not done

Accuracy matters more than eloquence.

When uncertain, say so.

Example response:

> “We first discussed entering Nebius as an FPC-like project, then realized the public repository requirement created an IP concern. We decided not to expose FPC itself and moved toward a separate personal-AI demonstrator. Later, we realized the mystery-gift users could provide the real-world test cohort.”

The system should be able to reconstruct useful chronological history.

## 9. VOCABULARY LEARNING SKILL

Implement a small longitudinal “Word of the Day” learning loop.

This is not a decorative content feature.

It should demonstrate that the personal AI can actively help the user develop something over time.

Every morning:

- introduce one word
- give a concise definition
- give one natural example sentence

During future interactions:

- occasionally reuse the word naturally when appropriate
- never force awkward usage

At night:

ask active-recall questions such as:

> “Do you remember what inchoate means?”

> “Did you use it today?”

> “Make me one sentence using it.”

Track vocabulary longitudinally.

Suggested fields:

- word
- introduced_at
- definition
- example
- recall_attempts
- correct_recalls
- user_sentences
- exposure_count
- last_reviewed_at
- mastery_state
- next_review_at

Suggested mastery states:

- new
- developing
- familiar
- mastered

Use a simple spaced-repetition approach.

Do not introduce endless new words while several previous words remain weak.

Example lifecycle:

```text
Day 1:
introduce “inchoate”

Night 1:
test recall

Day 3:
review again

Day 7:
use naturally in conversation

Later:
retire deliberate review once mastery appears strong
```

The product should keep an inspectable record of vocabulary learning.

## 10. SELECTIVE MEMORY

Do not save everything.

Distinguish between:

- ephemeral conversation
- durable fact
- thread
- commitment
- episode
- journal entry
- vocabulary item
- preference
- external discovery

The system should decide carefully what deserves persistence.

Every important persistent item should retain provenance.

The system should be able to answer:

> “Where did you get that from?”

The user should be able to:

- view remembered state
- edit incorrect state
- delete state
- mark something as outdated
- mark something as no longer relevant
- reactivate dormant Threads

Never silently treat an uncertain inference as a confirmed fact.

## 11. CLARIFICATION

Do not crystallize ambiguous conversation into durable state too aggressively.

Example:

> “I should probably learn Spanish sometime.”

Do NOT automatically convert that into a serious goal with deadlines.

Possible behavior:

- create a low-confidence exploratory Thread

OR

- leave it ephemeral

OR

- ask a clarification if it later becomes relevant

Example:

> “Remind me about that.”

If “that” is ambiguous, ask what the user means.

The public implementation may use:

- deterministic rules
- bounded classification
- Nemotron reasoning
- optionally Jev

Do NOT implement sophisticated proprietary FPC clarification/governance machinery.

## 12. EXTERNAL DISCOVERY / SOCIAL SEARCH

Do not initially attempt universal social-media access.

Instead, implement the higher-level behavior:

> “Watch this Thread.”

A Thread may optionally have:

```text
watch = true
```

When watched, a background process may periodically search selected external sources.

Initial sources should be practical and legally/API-accessible.

Possible sources include:

- general web search
- YouTube
- RSS feeds
- Hacker News
- Reddit if permitted
- other publicly searchable sources

Example:

```text
Thread:
“Long-lived agent memory architectures”

Watch:
ON
```

A background job finds a newly published paper or repository.

The system attaches the discovery to the Thread.

Later, the morning briefing may say:

> “Worth seeing: a new evaluation framework for persistent agent memory appeared yesterday. It looks closely related to the stale-memory problem you were exploring.”

The important feature is NOT “search social media”.

The important feature is:

external information is interpreted through the user’s continuing interests and Threads.

This feature is OPTIONAL for the first MVP.

## 13. SKILLS

Implement capabilities as modular Skills.

Initial Skills:

1. morning briefing
2. evening reflection
3. prospective reminder
4. vocabulary learning
5. thread resurfacing
6. shared-history recall

Later optional Skills:

7. watched-thread discovery
8. web search
9. calendar interaction
10. lightweight task execution

Skills should use a common interface where practical.

Conceptually:

```text
Skill
- name
- trigger types
- required context
- execute()
- possible state changes
- possible tool calls
- possible user-facing response
```

Do not create a giant generic plugin framework.

Keep the abstraction thin.

## 14. AGENT RUNTIME

Implement a thin custom event-driven runtime.

Do NOT introduce a heavy orchestration framework unless a concrete requirement appears that justifies one.

Everything entering the personal AI should be represented as an EVENT.

Initial event types may include:

- user_message
- morning_trigger
- evening_trigger
- commitment_check
- vocabulary_review
- external_discovery_result
- tool_result
- thread_resurface_check

The runtime should approximately perform:

1. receive event
2. identify user
3. load relevant structured state
4. retrieve relevant episodic context
5. identify applicable Skill or action
6. determine whether deterministic logic, Jev, or Nemotron should handle the decision
7. perform reasoning/classification
8. execute tools if required
9. generate a user-facing response if appropriate
10. update structured state
11. create/update Episode records
12. append AgentEvent audit record

Implement behind a clear abstraction:

```text
AgentRuntime.handle(event)
```

The SAME runtime must handle both:

- reactive events initiated by the user
- proactive events initiated by time/background jobs

Do NOT implement proactive behavior as a disconnected notification system.

Conceptual architecture:

```text
                 EVENT
                   │
         ┌─────────┴─────────┐
         │                   │
   User message        Scheduled event
                             │
         └─────────┬─────────┘
                   ↓
            Load user state
                   ↓
             AgentRuntime
                   ↓
       ┌───────────┼───────────┐
       │           │           │
deterministic     Jev       Nemotron
   logic      classification   reasoning
       │           │           │
       └───────────┴───────────┘
                   ↓
              run Skill
                   ↓
              call tools
                   ↓
        respond / take action
                   ↓
          update shared state
                   ↓
            record Episode
                   ↓
             append Event
```

Do NOT implement proprietary FPC governance, Story Tree, narrative engine, Hydra, or other private architecture in this public project.

Keep the runtime modular enough that a more sophisticated private decision engine could theoretically replace parts of it later.

## 15. RUNTIME DESIGN PRINCIPLE

Do NOT build this architecture:

```text
Chatbot
+
Reminder Service
+
Morning Cron
+
Journal Feature
+
Vocabulary Widget
```

Build this:

```text
                PERSONAL AI RUNTIME
                        │
        ┌───────────────┼───────────────┐
        │               │               │
 conversation          time            tools
        │               │               │
        └───────────────┼───────────────┘
                        ↓
                SHARED PERSONAL STATE
```

A morning briefing is simply the Runtime handling a morning event.

A reminder is the Runtime handling a temporal/commitment event.

An evening reflection begins from an evening event.

A user saying:

> “Actually, I finished that already.”

is a conversation event that updates the same state.

Everything should operate on the same underlying user state and history.

## 16. AI MODEL ARCHITECTURE

The hackathon requires use of Nebius infrastructure and at least one NVIDIA open-source model.

Use NVIDIA Nemotron through Nebius.

Preferred initial model strategy:

NEMOTRON NANO:

- normal conversational calls
- extraction
- summarization
- routine state updates
- straightforward tool use
- simple Skill execution

NEMOTRON SUPER:

- harder reasoning
- ambiguous decisions
- complex synthesis
- difficult planning or state interpretation

Do not use Ultra unless a demonstrated task requires it.

Implement model access through an abstraction so model selection can evolve.

Example:

ModelRouter

- fast_model
- reasoning_model
- classify_request()
- generate_response()
- reason_over_state()
- summarize_episode()

The system should visibly and meaningfully use Nemotron.

Do not hide all interesting decisions behind unrelated third-party models.

## 17. JEV

Jev may optionally be used for bounded classification tasks.

Good uses include:

- ephemeral / Thread / Commitment classification
- request type
- execute / clarify / defer
- Skill selection
- state transition classification
- urgency bucket
- whether an incoming message changes existing state

The architectural idea to test is:

not every internal decision requires generative reasoning.

Some decisions may be better represented as classification over known states.

Jev should NOT become the entire cognitive/runtime system.

Nemotron should remain central to the hackathon implementation.

## 18. BACKGROUND EXECUTION

Support scheduled/background execution.

Use Nebius Serverless Jobs where appropriate, or another minimal scheduling mechanism if necessary.

Required scheduled/background processes:

- morning briefing trigger
- evening reflection trigger
- commitment urgency scan
- vocabulary review scheduling
- thread resurfacing checks

Optional:

- watched-thread external discovery

Every background action should enter the same AgentRuntime as an Event.

Every meaningful background action should create an AgentEvent record.

## 19. DATA MODEL

Use PostgreSQL.

Minimum entities:

- User
- ConversationSession
- Message
- Thread
- Commitment
- Episode
- JournalEntry
- VocabularyItem
- Reminder
- SkillRun
- AgentEvent

Possible later entities:

- ExternalDiscovery
- MemoryFact
- ToolRun
- ThreadRelation

Prefer relational fields for important state.

Use embeddings/vector search as a supplementary retrieval mechanism.

Embeddings should NOT be the primary source of truth for:

- deadlines
- Thread state
- Commitment status
- vocabulary mastery
- explicit decisions
- action history
- Episode chronology

Structured state should remain inspectable.

## 20. EVENT LOG

Maintain an append-oriented AgentEvent log.

Useful events include:

```text
thread_created
thread_updated
thread_dormant
thread_abandoned
thread_completed

commitment_created
commitment_updated
commitment_completed
commitment_resurfaced

briefing_generated
reflection_started
reflection_completed

memory_corrected

word_introduced
word_reviewed
word_mastered

tool_called
tool_completed

skill_started
skill_completed

external_discovery_found
```

The log should help answer:

> “What happened?”

> “What did the assistant do?”

> “What changed?”

> “When did it change?”

Do NOT store hidden chain-of-thought.

Store concise observable reason/action metadata instead.

## 21. UI

Keep the visible product extremely small.

Primary views:

- CHAT
- TODAY
- THREADS

Optional fourth view:

- HISTORY / MEMORY

### CHAT

The persistent conversational relationship.

### TODAY

Should show:

- current morning briefing
- Power List
- urgent/open Commitments
- Word of the Day
- relevant resurfaced items
- evening reflection entry point when appropriate

### THREADS

Should show:

- active
- exploring
- waiting
- dormant
- optionally completed/abandoned

Allow user to inspect and edit Thread state.

### HISTORY / MEMORY

May show:

- Episodes
- journal entries
- remembered facts
- AgentEvent timeline
- vocabulary history
- things the assistant has done

Do NOT build a complicated enterprise dashboard.

The interface should feel calm, lightweight, personal, and mobile-first.

## 22. PRIVACY

This is a personal AI product.

Privacy should be visible in the design.

At minimum:

- isolate each user’s data
- never expose one user’s memories to another
- allow memory inspection
- allow deletion
- allow correction
- retain provenance
- avoid silently inventing memories
- store confidence when useful
- never expose chain-of-thought
- keep API credentials secret
- keep user-specific external integrations isolated

The architecture should remain compatible with future user-controlled/private storage.

## 23. WHAT NOT TO BUILD

Do NOT build:

- a generic autonomous agent framework
- a multi-agent society
- a complicated graph orchestration engine
- a full FPC implementation
- proprietary Story Tree logic
- proprietary governance machinery
- sophisticated private clarification architecture
- dozens of integrations
- universal social-media access
- elaborate emotional modelling
- unnecessary infrastructure
- a generic productivity dashboard
- a generic chatbot with RAG

This is an intentionally narrow demonstrator.

## 24. PROPRIETARY BOUNDARY

This public hackathon implementation must NOT contain the private FPC implementation.

It may demonstrate similar externally observable behaviors using deliberately conventional/simple mechanisms.

The following kinds of internal FPC machinery must remain outside this repository:

- proprietary narrative-memory architecture
- Story Tree internals
- governance architecture
- proprietary clarification machinery
- long-horizon decision policies
- proprietary world-model representation
- proprietary identity/state-transition mechanisms
- private execution primitives

Where possible, expose interfaces rather than proprietary implementation ideas.

Example:

```text
DecisionPolicy.decide(...)
```

The public repository may contain a simple implementation.

A future private system may replace that implementation entirely.

The public system should be useful and functional without revealing the architecture that makes FPC distinctive.

## 27. DEMO SCENARIO

The finished system should support a multi-day demonstration.

### DAY 1

User:

> “I need to submit my Nebius project next Friday.”

The system creates or updates a Commitment and Thread.

User:

> “I’m considering using Jev for bounded decisions.”

The system creates an exploratory Thread.

Morning vocabulary:

“inchoate”

Later:

User discusses an incomplete architecture idea.

The assistant may naturally use the word “inchoate”.

### DAY 2

Morning:

The system generates a Power List based on current state.

During conversation:

User says:

> “The frontend is finished.”

The system updates project state.

Evening:

Assistant:

> “How did things go today?”

User:

> “I finished the frontend but didn’t get to the evaluation.”

The system:

- stores the journal entry
- updates project state
- keeps evaluation unfinished
- updates Episode history

Then:

> “Do you remember what inchoate means?”

User answers.

The system records recall performance.

### DAY 4

The deadline is approaching.

The system notices shrinking slack.

It proactively says:

> “The evaluation work still looks open. You estimated about three hours for it, and the submission deadline is now close enough that I think it needs attention today.”

### DAY 5

A watched Thread finds an external item.

The assistant surfaces:

> “I found a new repository related to persistent-agent memory evaluation. It looks closely connected to the stale-memory question you were exploring.”

### DAY 6

User asks:

> “What have we done on the Nebius project?”

The assistant accurately reconstructs:

- important decisions
- completed steps
- unresolved issues
- actions it took
- relevant chronology

The answer should come from explicit Episode/state data, not fabricated recollection.

## 28. SUCCESS CRITERIA

The product succeeds if:

1. The assistant remembers important state across sessions.
2. The user can inspect and correct that state.
3. It can maintain loose mental Threads without converting everything into tasks.
4. It understands unfinished Commitments.
5. Time materially changes what it surfaces.
6. Morning briefings reflect real current state.
7. Evening conversation changes tomorrow’s state.
8. The system can accurately recall shared history.
9. The vocabulary loop persists across days.
10. The user can understand why something was resurfaced.
11. Proactive behavior comes through the same personal AI relationship.
12. Nemotron and Nebius are genuinely important to the implementation.
13. The experience feels like one coherent product rather than disconnected features.
14. The architecture demonstrates the product thesis without exposing proprietary FPC internals.

## 29. IMPLEMENTATION APPROACH

Before writing significant code:

1. Inspect the existing repository if one exists.
2. Describe the current architecture.
3. Propose the minimum architecture required for this specification.
4. Define the database schema.
5. Define the Event model.
6. Define the AgentRuntime interface.
7. Define the Skill interface.
8. Define the major state transitions.
9. Identify ambiguous product decisions.
10. Produce a Milestone 1 implementation plan.

Do NOT attempt the entire specification in one pass.

Implement Milestone 1 first.

After each milestone:

- run tests
- demonstrate the primary user flow
- verify persistence across sessions
- inspect database state
- identify failure modes
- update documentation
- stop before progressing if the current continuity loop does not work
